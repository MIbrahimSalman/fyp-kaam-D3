6.7.5 Implementation Policies

The implementation policies fix the rules that each module family must follow regardless of which
algorithm it contains. They cover controllers, routing, persistence, and the user interface, and they are
the rules that the automated tests check.

6.7.5.1 Controller Policy

All controllers implement a common method that accepts an immutable traffic snapshot, intersection
configuration, and decision context, then returns a request with explanation fields. They cannot write
global state, call TraCI, or suppress the record of a rejected action. The fixed controller, pressure-
inspired controller, and learned policy therefore differ in decision logic while sharing phase identifiers,
decision intervals, safety constraints, and applied-event recording. Deterministic evaluation disables ex-
ploration and seeds every permitted stochastic operation. The safety filter verifies phase membership,
minimum green, required clearance, maximum priority duration, and current ownership before an action
reaches the adapter. If a policy is unavailable, the current legal phase is held and each such decision is
counted; transfer to the configured baseline at a legal boundary is planned for FYP-II. This common in-
terface is central to a fair comparison because it prevents one controller from receiving more permissive
movements or direct simulator privileges. Explanation fields are retained for later error analysis.

6.7.5.2 Routing Policy

The graph builder derives nodes and edges from validated SUMO vehicle movements, including allowed
classes and turn continuity. Cost providers are composable but must state units, observation time, fall-
back behavior, and whether link travel time already includes queue delay. This metadata prevents the
routing service from adding overlapping estimates or comparing seconds with an unnormalized conges-
tion score. A published route plan is immutable, and the mission points to exactly one current version.
Revisions are accepted only through Algorithm 1, which compares paths under one cost snapshot and
applies feasibility, hysteresis, persistence, and cooldown rules. A hard closure overrides ordinary cost
and invalidates an affected remaining path immediately. Before publication, the route is checked from
the ambulance’s current edge to the destination and given a revision cause. The routing service never
actuates signals; it supplies versioned plans to the corridor coordinator, which can then cancel or create
priority requests consistently.

6.7.5.3 Persistence Policy

In FYP-I the store writes structured configuration, events, missions, routes, and metrics as versioned
files, and the FYP-II database will add schema migrations and referential constraints, while large videos,
model files, and logs may remain checksummed external artifacts with provenance. Raw high-frequency
state can be downsampled for persistence only when the sampling interval and aggregation rule are
recorded in the metric definition. Completed run configuration is immutable, and derived summaries
retain their source run identifiers and analysis version. Secrets, machine-specific credentials, and un-
portable local paths are excluded from research exports; licensed artifacts are referenced rather than
redistributed when necessary. FYP-I uses a file-backed store behind the repository interface, and Post-
greSQL is planned for structured records in FYP-II. The domain schema and integrity rules remain
independent of that choice so a storage migration cannot change the meaning of an experiment. A
persistence failure follows the bounded behavior in Table 6.4 rather than silently discarding events. Re-
covery records state whether buffered evidence was restored.

6.7.5.4 User-Interface Policy

The user interface is a view and command boundary, not a second control plane. Colors are supple-
mented with text and symbols so congestion, corridor state, or failure is not conveyed by color alone.
Values display their units, source mode, freshness, and invalid state where applicable. Schematic predic-
tions remain visually distinct from measured results, and an uncalibrated video proxy is not labeled as a
physical queue or speed. The interface does not display “time saved” until a valid reference run exists
under the same comparison manifest, and it exposes configuration differences when direct comparison

is unsafe. Commands receive validation errors tied to fields, while connection loss leaves the experiment
running and allows a client to reconnect from the current event cursor. These policies implement the
wireframe intentions in Section 4.8 and ensure that a polished display cannot conceal stale data, fallback
intervals, missing runs, or incomplete evidence.

6.7.6 Testing Strategy

Unit tests cover cost functions, route continuity, hysteresis, metric calculations, schema validation, fresh-
ness rules, and corridor transition guards. Property or invariant tests generate action sequences to ensure
incompatible greens are never requested for application, one component owns each intersection, obso-
lete route versions cannot activate priority, and cancellation eventually reaches IDLE through RECOV-
ERY. Integration tests use small SUMO networks to validate single-step ownership, detector-to-state
messages, route application, fallback, and persistence ordering. Scenario tests replay fixed seeds for
normal control, closure rerouting, no-route, invalid actions, and priority timeout; tests for stale data,
controller loss, persistence failure, and dashboard disconnect are planned for FYP-II. Contract fixtures
allow components to be replaced by stubs without weakening field validation. Research verification re-
mains separate from software correctness: passing these tests shows that the implementation follows its
specification, but it does not establish that a policy improves traffic or emergency travel. The matched
experiments in Chapter 5 provide that evidence, while test results explain whether a failed experiment
reflects the policy or a software defect. At the end of FYP-I the automated suite contains 147 tests in
17 files, most of which run real SUMO on small scenarios; they include a random controller over 5,000
steps with zero safety violations, A* against Dijkstra on 200 random cost sets, identical metrics for the
same seed, and a dashboard session from dispatch through closure and rerouting to arrival.

6.7.7 Coding, Build, and Maintainability Policies

Python modules use type hints, Ruff formatting and linting, pinned dependency versions, and docstrings
for public interfaces. React components separate data acquisition from presentation so a visual revision
cannot change experiment ownership. Configuration is stored in validated versioned files rather than
scattered constants, and secrets remain outside exported manifests. The full test suite, including headless
SUMO scenarios, runs before a revision is used for evidence. Experiment releases are tagged and
their commit identifier is written into each run manifest. The repository structure separates application
services, controllers, routing, perception, simulation, dashboard, contracts, scenarios, and experiment
artifacts, as listed in Section 6.7.9. Small interfaces allow a tracker, learned policy, database engine, or
dashboard transport to change without rewriting the central loop, while versioned contracts force such
changes to declare any effect on recorded evidence.

6.7.8 Continuous Integration and Deployment

The proposed continuous-integration pipeline runs formatting, linting, type checks, unit tests, contract
fixtures, schema validation, and a minimal headless SUMO scenario. In FYP-I there is no hosted pipeline
yet: every change is linted and the full test suite, including headless SUMO scenarios, is run before it
is merged into the main branch. A build that changes an interface or metric definition must update its
version and associated fixtures. Deployment for the prototype remains a documented local environment
rather than a claimed production service. A tagged demonstration build includes dependency locks, val-
idated scenarios, required model checksums, and migration state so another team member can reproduce
the same prepared workflow. The headless smoke scenario verifies process launch, one controlled step
sequence, valid signal application, event persistence, and a clean terminal state without requiring the
dashboard. Research experiments are not automatically promoted merely because software tests pass;
the matched evaluation protocol remains a separate activity. Failed checks block an evidence release, and
bypasses must be recorded rather than hidden. If an external model or licensed video cannot be pack-
aged, the build manifest records its checksum and acquisition instructions while keeping the protected
artifact outside the archive.

6.7.9 Source Code Organization

The repository separates API and application services from controllers, routing, perception, simulation
adapters, interface contracts, dashboard code, scenarios, and experiment artifacts. Tests mirror those
boundaries, while generated outputs and large external artifacts remain outside source modules. Con-
figuration is versioned and validated instead of embedded in code. This arrangement keeps research
implementations replaceable, makes ownership visible during review, and avoids circular dependen-
cies between interface, simulation, and persistence concerns. Domain objects and contracts occupy a
low-dependency package that does not import the dashboard or infrastructure adapters. Controller im-
plementations share an interface but do not import each other, allowing fixed, pressure-inspired, and
learned policies to be selected by configuration. Scenario manifests reference networks and demand
files through portable paths and checksums. Analysis scripts read retained records rather than private
controller state. Documentation accompanies public interfaces and configuration schemas. The FYP-I
repository follows this organization. The manzil package contains sim, control, routing, corridor,
experiments, perception, scenarios, and api; dashboard holds the React code, scenarios the
network and signal configuration, kaggle the GPU job definitions, tests the automated tests, and
results the retained summaries and figures. Large datasets and run outputs stay outside version con-
trol and are referenced by checksum.

6.8 Conclusion

The design assigns one clear owner to every mutable resource and makes observation source, simulation
time, units, route version, requested action, and applied action explicit. The high-level architecture keeps
presentation and perception outside the single-writer simulation path, while component responsibilities
and data contracts make integration boundaries testable. The domain model and sequences preserve
causal links from scenario and snapshot through controller request, safety decision, route revision, cor-
ridor transition, and durable event. Guarded recovery and bounded fallbacks ensure that a failure does
not leave an unexplained signal or apparently live dashboard. Common controller interfaces support the
intended progression from fixed and pressure-inspired baselines to a learned policy, and versioned rout-
ing enables a moving corridor without granting the pathfinder direct signal authority. The architecture is
modular enough for team implementation on one machine and leaves distribution as a profiling decision,
not an assumption. It also preserves failed runs and negative research outcomes as evidence instead of
hiding them behind interface behavior.
