Chapter 4 Software Requirement Specifications

This chapter translates the reviewed problem and evidence into a specification for the Manzil research
prototype. The requirements describe observable behavior rather than implying that every item has al-
ready been implemented. Where the available repository evidence does not support a measured thresh-
old, the text states a design target or requires profiling before a value is fixed. The specification gives
particular attention to reproducibility, legal signal transitions, observation freshness, route-version con-
sistency, and visible failure handling because these properties determine whether later experiments can
be interpreted. It also separates the video-perception workflow from SUMO-based control experiments
so that estimated observations are not silently presented as simulator ground truth. Account manage-
ment, public dispatch integration, traffic enforcement, clinical response prediction, and physical signal
deployment remain outside the approved scope. The resulting requirements provide a contract for the
architecture in Chapter 6 and a traceable basis for the evaluation procedures in Chapter 5.

4.1 List of Features

The prototype is organized into six feature groups that follow the operator's experimental workflow
from configuration to evidence export. The grouping prevents a user-interface screen or implementation
library from being mistaken for a requirement and clarifies which service owns each outcome. It also
shows that emergency operation is not an isolated routing feature: a valid mission depends on scenario
state, traffic observations, signal control, monitoring, and durable records. The following statements
summarize those groups before the individual functional requirements define testable behavior.

   1. The operator can select a network, demand profile, controller, seed, incident, duration, and op-
       tional emergency mission before a run begins.

   2. The perception workflow can process licensed recorded video into detections, tracks, road-region
       observations, and timestamped aggregate measures with confidence information.

   3. The simulation workflow advances SUMO through one owner, reads traffic state, applies fixed or
       adaptive requests, and preserves legal phase transitions.

   4. The emergency workflow validates endpoints, computes a dynamic path, applies stable rerouting,
       activates bounded moving priority, detects passage, and recovers normal control.

   5. The monitoring interface presents map state, signals, traffic indicators, ambulance route, corridor
       state, warnings, and the current data-source mode.

   6. The experiment service retains immutable configuration, events, metrics, software versions, seeds,

and termination state for comparison and export.

4.3 Quality Attributes

Manzil's quality model separates broad software qualities from the individually testable non-functional
requirements. The qualities below explain why the requirements matter to this research prototype, while
CHAPTER 4. SOFTWARE REQUIREMENT SPECIFICATIONS  28

Section 4.4 assigns stable identifiers to the corresponding acceptance conditions. The distinction is
important because a feature may execute without producing credible research evidence. For example, a
controller can return an action and still violate reliability if the applied phase, effective step, or fallback
reason is lost. Similarly, a dashboard can appear responsive while showing stale observations. Manzil
therefore treats usability, reliability, security, performance, maintainability, extensibility, and traceability
as constraints on the complete workflow rather than as cosmetic objectives. Each quality is interpreted
within a simulation and recorded-video setting; none is presented as evidence of certified public-road
operation.

4.3.1 Usability

The interface is designed for a trained research operator who must configure a scenario, observe a
run, initiate a simulated ambulance mission, and inspect retained evidence without switching among
unrelated tools. Inputs use project terminology and display units, validation state, data source, and
freshness beside the value that they qualify. Navigation preserves the selected run and mission context
so that moving between the network overview, perception detail, emergency route, configuration, and
analytics screens does not silently change the experiment. Status is not communicated by color alone:
labels and symbols distinguish normal, stale, fallback, invalid, and disconnected states. Destructive or
irreversible actions, such as stopping a run or replacing an active route version, require clear confirmation
or are mediated by backend validation. These provisions do not claim that a formal usability study has
been completed. They define observable interface behavior that can later be checked through task-based
review using the proposed screens in Section 4.8.

4.3.2 Reliability and Integrity

Reliability concerns the preservation of valid state and evidence when a component is slow, unavailable,
or produces an invalid request. One orchestrator and one SUMO adapter own simulation stepping and
signal actuation, which prevents two services from advancing the same clock or issuing competing phase
changes. Requested actions are stored separately from applied actions so the safety filter's intervention
remains visible. A run configuration becomes immutable after start, route revisions are monotonically
versioned, and corridor requests retain the route version that authorized them. Missing observations
remain missing rather than being converted to zero, while stale observations are rejected or handled
through a declared fallback. Terminal run states include completed, stopped, failed, and incomplete,
each with a reason. Integrity therefore means that an unsuccessful experiment remains interpretable;
it does not mean that every component is continuously available. Recovery and fallback behavior are
specified explicitly in the use cases, risk register, and Chapter 6.

4.3.3 Security and Confidentiality

Manzil is not a public dispatch or traffic-control service, but its development data still require controlled
handling. Recorded video must be licensed, public under suitable terms, or specifically authorized
for team use. Raw video and model artifacts remain external files referenced through provenance and
checksums rather than being copied indiscriminately into experiment exports. Machine credentials,
private paths, and access tokens are excluded from run manifests. The proposed dashboard is an operator
interface for a controlled laboratory environment and does not introduce public user registration. If
authentication is later required for deployment, it must be added as a separate verified requirement rather
than assumed in this deliverable. Exported research records should contain scenario and measurement
identifiers but no unnecessary personal data. These boundaries provide proportionate confidentiality
for the stated prototype while avoiding unsupported claims about production authorization, encryption
infrastructure, or compliance with operational emergency-service policies.

4.3.4 Performance

Performance is defined relative to the chosen simulation step, control interval, video workload, and
demonstration hardware. The control path must complete its decision before the configured deadline for
the step in which the action becomes effective; otherwise the interval is marked late and a declared base-
line or safe continuation is used. Video inference runs in a bounded worker so a slow model cannot block
simulation stepping or an API request indefinitely. Dashboard delivery is a lossy view of authoritative
state, allowing an inactive client to skip intermediate frames without delaying control. Route computa-
tion and comparison queries are profiled separately from simulation actuation because their acceptable
latency depends on network size and update frequency. FYP-I profiling on the synthetic grid provides
first measured values. One SUMO step with medium demand takes about 1 ms through libsumo, a route
computation takes less than 0.1 ms, and a batch of 60 full-length runs completes in about 100 s on four
CPU cores. The fine-tuned detector needs about 6.8 ms per image on a Tesla T4, and detection with
tracking runs at 40 to 66 frames per second on the same GPU. These values describe the grid and the
stated hardware only; thresholds for the Lahore network will be set after it is profiled in FYP-II, and
every measurement identifies its workload, hardware, and software versions.

4.3.5 Maintainability and Reusability

Maintainability is supported through typed, versioned contracts and replaceable implementations behind
stable responsibilities. Fixed-time, rule-adaptive, and learned controllers share one request interface and
therefore receive the same snapshot fields and legal phase constraints. The repository boundary allows
CHAPTER 4. SOFTWARE REQUIREMENT SPECIFICATIONS  30

early file-backed persistence to be replaced by PostgreSQL without changing the meaning of a run,
while the perception boundary permits a detector or tracker to change only when its model version and
output semantics are declared. Configuration is stored in validated files rather than scattered constants,
and public interfaces are documented with units, identifiers, timing semantics, and failure behavior.
Tests target cost functions, route continuity, freshness rules, schema validation, and corridor invariants
independently of the final dashboard. Reuse is limited to components whose assumptions remain valid;
a model, road network, or phase plan is not treated as reusable merely because its file can be loaded.
These rules reduce coupling while preserving the provenance required for research comparison.

4.3.6 Extensibility and Traceability

The design leaves controlled extension points for additional controllers, perception models, route-cost
providers, scenarios, and visualizations. An extension must implement the existing contract or introduce
an explicit schema version, and it must not acquire direct TraCI access or bypass the common safety
filter. New measurements include a definition, unit, interval, and source run identifiers so previous
and revised metrics cannot be combined silently. Traceability connects functional requirements to use
cases, screens, architecture components, events, and planned tests through stable identifiers and cross-
references, and Table 7.20 links each requirement to its test cases. Every exported comparison retains
the run manifest, seed coverage, controller version, metric version, and failed-run status. This approach
allows the prototype to grow without changing the interpretation of earlier evidence. Extensibility is
therefore not an unrestricted plugin claim; it is the ability to replace or add a component while declaring
the effect on control ownership, data contracts, and reproducibility.

attribute above. Privacy is limited to the handling of licensed or team-authorized video and does not
imply a production governance framework. These non-functional requirements also define how nega-

4.5 Assumptions

SUMO and TraCI are required for controlled traffic experiments [17, 22]. A selected network must
contain legal lane connections and signal plans after import and manual cleanup, and representative
routes must be validated before it is used for comparison. Video sources require sufficient visibility,
a documented license or team authorization, and annotations appropriate to the selected measure. The
simulation assumes one clock owner, nonnegative route costs, and emergency endpoints on ambulance-
accessible edges. It also assumes that configured phase transitions reflect the validated simulation net-
work; they are not certified timings for physical signal hardware. The dashboard is an operator and
evaluator tool rather than an autonomous public dispatch system, and a displayed route does not consti-
tute operational navigation advice. When an assumption cannot be met, the affected workflow must stop
or disclose a bounded fallback. It must not silently substitute a different network, data source, time unit,
or observation mode because that would make later comparisons irreproducible.

React and FastAPI are fixed by the approved proposal for the interface and application service bound-
ary [23, 24]. Python is used for perception, reinforcement learning, and the TraCI interface. In FYP-I
the dashboard receives state over a WebSocket and draws the map as plain SVG without a map library.
PostgreSQL and Docker were not needed for the prototype: run records are stored as versioned files, and
a database is planned for FYP-II behind the same repository boundary. These assumptions are deliber-
ately narrower than a production deployment specification. Manzil is evaluated as a controlled prototype
on prepared networks, not as an interface to public signal controllers or ambulance dispatch infrastruc-
ture. A selected video source must have suitable permission and sufficient visibility for the intended
annotation task, while the simulation network must be checked for lane connectivity, valid traffic-light
programs, and ambulance-accessible routes. If any assumption fails, the run must be rejected or marked
with an explicit limitation instead of substituting an undocumented configuration. This treatment keeps
CHAPTER 4. SOFTWARE REQUIREMENT SPECIFICATIONS        33

dependencies traceable and prevents a convenient library choice from becoming an unsupported archi-
tectural claim.

4.6 Use Cases

The primary actor is a research operator who configures experiments, observes their progress, initiates
a simulated emergency mission, and exports evidence. SUMO, recorded video, and the experiment
store support those actions but do not independently choose research parameters. Evaluators consume
dashboard views and exported records without receiving control privileges. Figure 4.1 presents this
boundary and connects the operator to eight goal-oriented interactions. Configuration and simulation
appear separately because validation must finish before the single clock owner starts a run. Dispatch,
corridor monitoring, and rerouting are also distinct so that a route revision cannot be treated as an
invisible side effect. Tables 4.3­4.10 then specify a summary, conditions, special requirements, the
basic actor­system exchange, and alternative behavior for each interaction. Collectively, they test more
than the successful interface path: invalid endpoints, stale streams, no-route cases, controller failure,
incompatible comparisons, and termination reasons must all produce observable outcomes. The use
cases therefore define acceptance evidence as well as operator interaction.

4.7 Hardware and Software Requirements

The development environment must support two different workloads: repeated model or controller ex-
periments and a prepared, repeatable demonstration. The distinction avoids presenting a high-end train-
ing machine as a mandatory deployment requirement. The hardware and software below are the envi-
ronment actually used in FYP-I; capability statements remain only for the Lahore network, which has
not yet been selected. Software choices are separated from hardware so that a library can be versioned or
replaced without changing the resource description. Tables 4.11 and 4.12 list the resources and pinned
versions behind every reported result. The demonstration uses the same network, controller configura-
tion, metric schema, and software versions as the retained evaluation record even when it runs fewer
scenarios.

4.7.1 Hardware Requirements

Table 4.11 lists the machines used in FYP-I. The team laptop has an Intel Core i7-8650U processor and
16 GB of memory but no NVIDIA GPU; it runs SUMO, all controller and routing experiments, the
API, and the dashboard. Long coding and experiment sessions also ran on cloud Linux machines with
the same pinned software. Detector training and video tracking need a GPU, so they ran on Kaggle
with two Tesla T4 GPUs of 15 GB each, and only small outputs such as metrics, plots, and the 19 MB
model weights were brought back. The DQN was trained on CPU in 17 minutes because the grid is
small. Large datasets stay on Kaggle and are referenced by name and checksum rather than copied.
The demonstration therefore needs only a CPU machine: it shows prepared perception results and runs
SUMO, the controllers, and the dashboard live.

4.7.2 Software Requirements

In Table 4.12 each technology is tied to a task and to a configuration item that must be recorded. SUMO
and TraCI provide the authoritative simulation environment and control interface. Python supports per-
ception, routing, control, experiment orchestration, and analysis, while React and FastAPI form the
interface boundary from the approved proposal. All versions are pinned in the project configuration so
every machine installs the same software; SUMO is installed from the Python package index rather than
a system installer for this reason. The synthetic grid was generated with SUMO's own network gener-
ator, so OpenStreetMap tools and NetEdit are reserved for the Lahore network in FYP-II. Git commit
identifiers and the pinned versions are written into every run manifest.

4.9 Database Design

This section defines the logical data model that keeps experiments, observations, control decisions, and
emergency missions traceable. The model is independent of the storage engine. In FYP-I it is realized
as versioned files: every run folder holds a manifest with the configuration, seed, software versions,
commit, and checksums, a metrics file, time series, signal events, applied controls, and mission records
with route versions and corridor events. A relational database behind the same model is planned for
FYP-II, when the five-screen dashboard needs cross-run queries.

4.9.1 Entity Relationship Diagram

Persistent data is reserved for configuration, observations, decisions, missions, and outcomes that re-
quire audit or comparison. The live road graph, TraCI subscription, and frame buffers remain runtime
state, while raw video is retained as a checksummed external artifact. Figure 4.8 presents the complete
conceptual model with blue entity rectangles, green attribute ovals, amber relationship diamonds, and
cardinalities beside relationship lines. The dashed regions separate experiment configuration and evi-
dence, observation and control records, and emergency routing and priority. Figures 4.9, 4.10, and 4.11
enlarge those regions so keys, attributes, and named relationships remain readable at normal print size.
Primary keys are underlined, foreign keys are marked FK, and optional ownership is expressed explic-
itly. The diagrams describe a proposed logical schema and do not claim that a production database has
already been populated.

Figure 4.9 enlarges the experiment-configuration region of the overview. A Scenario defines immutable
network and demand versions and may be reused by several ExperimentRun records. Each run fixes
its seed, controller version, status, and configuration at start, then owns its MetricSample and Artifact
records. The records relationship is deliberately named because metrics and exported files are evi-
dence produced under one run rather than free-standing data. Metric samples retain a definition version,
interval, value, and unit, while artifacts retain a type, URI, checksum, and provenance. These associa-
tions prevent results from different seeds or controller configurations from being combined without their
originating run. They also permit an evaluator to trace a displayed chart or exported file back to the
configuration that produced it.

idence. Simulation observations reference an ExperimentRun; offline video observations reference a
VideoJob. Exactly one owner is present for each observation, so a record cannot be presented simultane-
ously as simulator truth and video-derived evidence. The Observation entity carries source mode, entity
identifier, effective and validity times, values, units, and confidence. A ControlDecision refers to the run

4.10 Risk Analysis

Table 4.15 records technical and research risks that could invalidate the prototype or its conclusions.
Likelihood and impact are qualitative planning judgments rather than measured probabilities. The
highest-consequence risks concern invalid signal phases, irreproducible results, unsuitable map imports,
and evidence that cannot be legally or reliably used. Each mitigation is paired with a bounded fallback
so that the team can preserve an honest deliverable if a preferred component fails. For example, a docu-
mented synthetic network is preferable to an unverified real-map extract, and a negative reinforcement-
learning result is preferable to tuning on the final test scenarios. The register also treats timing drift,
route oscillation, occlusion, and reward imbalance as system-level concerns rather than isolated coding
defects. These risks are revisited through invariant tests, scenario checks, provenance records, and the
controlled comparisons defined in Chapter 5; unresolved items must remain visible in the final limita-
tions rather than being converted into unsupported performance claims.

4.11 Conclusion

The specification centers on traceability and failure visibility rather than on a collection of loosely con-
nected features. It requires one simulation-clock owner, legal signal transitions, stable route revision,
explicit observation freshness, immutable run configuration, and comparisons that cannot hide incom-
patible settings or failed trials. Functional requirements define what the operator and services must
observe, while non-functional requirements constrain timing, ownership, privacy, auditability, and re-
covery. The use cases exercise both successful and failed paths, the wireframes show how critical state
and provenance remain visible, and the data model preserves the route and decision history needed
for later analysis. The risk controls connect those requirements to bounded fallbacks and verification.
Chapter 5 converts the specification into a staged research protocol, and Chapter 6 assigns each mutable
resource and interface to a clear architectural owner. Implementation status is reported separately in
Chapter 7 so that a specified feature is never presented as completed evidence.
