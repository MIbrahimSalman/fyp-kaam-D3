Chapter 6 High-Level and Low-Level Design

This chapter maps the requirements and methodology to a service-oriented prototype design that can
be implemented incrementally on the team's available machines. The decomposition protects experi-
mental determinism by assigning the simulation clock and all signal actuation to one adapter. The API,
dashboard, perception worker, controllers, routing logic, and experiment store exchange typed mes-
sages without competing for that authority. The design also separates a requested decision from the
action applied after safety checks, preserves the source and effective time of every traffic snapshot, and
binds corridor requests to an immutable route version. These choices support replay and fault diagnosis
without requiring a prematurely distributed deployment. Interfaces may initially be implemented as in-
process modules, provided that they retain the same ownership boundaries and contracts. The chapter
moves from architecture and domain objects to interaction sequences, state transitions, data contracts,
synchronization, failure handling, module policies, and testing so each important requirement has a vis-
ible design consequence. In FYP-I the design was implemented as one Python package with a separate
React dashboard. Chapter 7 maps each design component to the module that implements it.

6.1 System Overview

The system must support repeatable research runs, an interactive demonstration, and post-run analysis
without allowing presentation concerns to alter experimental state. Its main design goals are determin-
istic ownership of state changes, replaceable controller and perception implementations, explicit time
and units, safe corridor transitions, immutable run configuration, and visible failure. Performance is
optimized only after these properties are preserved because a faster result is not useful when its source,
phase legality, or causal order is uncertain. The design assumes one machine or a small development
deployment for the FYP prototype. Logical separation therefore does not imply a network service for
every box in the diagrams. The orchestrator, controllers, routing logic, and repositories may begin as
in-process modules behind typed interfaces, while video inference can move to a bounded worker when
profiling shows it would block the control loop. This approach keeps deployment manageable but pre-
serves a path to isolate resource-heavy components without changing experimental semantics.

6.1.1 Operator Interface and Commands

The operator uses a React dashboard for configuration, monitoring, emergency, and analysis tasks. Com-
mands pass through FastAPI validation before reaching the experiment service or orchestrator. The in-
terface cannot step SUMO, apply a phase, or alter an active run's immutable configuration. Responses
include source, simulation step, freshness, and status so the dashboard can distinguish current evidence

from a stale or unavailable view. Configuration commands resolve network, controller, seed, duration,
incident, mission, and metric identifiers before a run begins. Monitoring queries expose requested and
applied actions separately, while emergency commands return the route version and corridor state af-
fected by the request. The evaluator can inspect completed and failed runs without receiving mutation
privileges. A disconnected browser may reconnect from the current snapshot and event cursor, but
it cannot replay an old command automatically. These rules make the graphical interface useful for
demonstration and review without creating a second, poorly controlled path into the traffic simulation.

6.1.2 Traffic Observation and Simulation

SUMO provides authoritative traffic state for controlled experiments, while a bounded perception worker
supports recorded-video observation. The traffic-state service normalizes either source without present-
ing video proxies as simulator measurements. Only the SUMO/TraCI adapter owns simulation stepping,
subscriptions, and applied signal changes. Perception reports model version, input provenance, confi-
dence, and freshness, preserving a clear record of what information was available to each decision. A
simulator snapshot can include exact vehicle, lane, signal, and route values available through TraCI. A
video snapshot contains only quantities justified by the selected detector, tracker, road regions, and cal-
ibration; missing physical values remain unavailable instead of being replaced by zero. Both snapshots
identify the time at which values became effective and the period for which they remain valid. The con-
trol loop uses one declared source mode per experiment, while offline perception jobs can be assessed
independently against labelled footage. This boundary prevents the report from treating visual detection
output as equivalent to controlled simulator ground truth.

6.1.3 Adaptive Control and Emergency Routing

Normal traffic control and emergency priority share the safety filter but remain separate decision con-
cerns. Fixed-time, pressure-inspired, and learned controllers return requested actions through a common
interface. Routing creates immutable, time-costed ambulance paths, and the corridor coordinator trans-
lates the current route into bounded priority requests. Neither module actuates a signal directly; every
request must satisfy legal phase, clearance, ownership, expiry, and recovery rules. The common con-
troller interface supplies the same snapshot, legal phases, decision interval, and explanation fields to
each normal strategy so comparison is not distorted by different privileges. Emergency operation is su-
pervisory: it temporarily owns selected intersections through an explicit state machine and returns them
to a valid normal boundary after passage, cancellation, or timeout. Rerouting creates a new route ver-
sion and cancels obsolete future requests before activating the revised look-ahead set. Separating route
choice, corridor priority, normal control, and safety enforcement permits useful ablation experiments

6.2 Design Considerations

The design considerations record the conditions the architecture relies on, the limits it must respect, the
principles used to resolve trade-offs, and the main development decisions taken. They explain why the
architecture favours single ownership, explicit versions, and visible failure over maximum distribution
or speed. Where the prototype uses a simpler form, such as a synthetic network or file-based storage,
the subsection says so.

6.2.1 Assumptions and Dependencies

The design assumes a validated SUMO network, legal traffic-light programs, reproducible demand files,
and approved recorded video when perception experiments are performed. It depends on TraCI for
simulator control and on versioned model artifacts and repositories for repeatable evidence. A single
development machine is sufficient for initial integration, although detector training may require sepa-
rate GPU capacity. Missing maps, checkpoints, or video sources therefore produce explicit fallbacks or
blocked experiments rather than hidden substitutions. Network preparation must resolve disconnected
edges, prohibited movements, signal programs, and ambulance-compatible routes before a scenario is
accepted. Demand generation exposes its seed and distribution parameters so repeated runs can be
paired. Video processing assumes that clip provenance, model checksum, road regions, and any calibra-
tion are available. The repository must retain configuration and causal events even when large artifacts
remain external files. These assumptions are verified at configuration time where possible; unmet condi-
tions become validation errors, declared limitations, or a documented synthetic-network fallback rather
than undocumented changes to the experiment.

6.2.2 General Constraints

The prototype cannot assume city-wide live sensors, traffic-authority deployment, or emergency-service
integration. Evaluation is simulation based, with recorded video used only for perception validation.
The core scope permits one active emergency mission, every signal transition must follow the validated
program, and a run's configuration becomes immutable at start. Failed runs remain visible, while no
dashboard action can bypass backend validation. These constraints prevent a polished demonstration
from being confused with operational deployment. The selected Lahore network must remain small
enough for repeated seeded experiments and readable inspection of imported connections. The sys-
tem does not claim certified preemption, field latency, legal authority, or direct control of real signals.
Learned controllers operate within the same legal action space and decision schedule as baselines, and
training-only tuning cannot use held-out evaluation scenarios. Resource limits may require offline detec-
CHAPTER 6. HIGH-LEVEL AND LOW-LEVEL DESIGN  71

tor inference, compact networks, or a documented synthetic grid. Such reductions are acceptable only
when the report discloses them and conclusions remain bounded to the tested network, demand, footage,
models, and computing environment.

6.2.3 Goals and Guidelines

The design prioritizes traceability, deterministic ordering, safe actuation, replaceable research compo-
nents, and honest reporting of unavailable evidence. Each mutable resource has one owner; messages
carry version and effective time; requested and applied actions remain distinct; and fallback behavior is
bounded and labelled. Interfaces are small enough for contract testing, and diagrams describe logical re-
sponsibilities rather than claiming every component is already deployed as a separate service. Naming,
units, source modes, and terminal states remain consistent across the API, database, logs, interface, and
report. A component rejects an unknown schema, expired snapshot, illegal phase, disconnected route, or
incompatible comparison rather than trying to infer intent. Experiments retain failures, exclusions, and
fallback intervals so favorable summaries cannot hide them. Performance optimization follows profiling
and must not bypass validation or remove evidence. A change is accepted only when its owner, inputs,
outputs, time semantics, failure behavior, and effect on reproducibility can be stated and tested.

6.3 System Architecture

The Manzil architecture follows the component boundaries introduced in Section 6.1.4 and refines them
into objects that can be implemented and tested independently. The dashboard and API form the presen-
tation boundary, while the orchestrator, traffic-state service, controller registry, routing service, corridor
coordinator, safety filter, simulation adapter, and experiment store form the application core. This parti-
tion keeps visualization outside the authoritative control path and assigns every mutable resource to one
owner. Communication may initially use in-process calls, but each interaction retains a typed request
or event contract so that later separation does not change experimental meaning. The architecture also
distinguishes a proposed action from an applied action, a traffic observation from its source, and a route
from the version that authorized corridor activity. These distinctions make replay and fault diagnosis
possible because each state change can be connected to its input snapshot, policy, safety decision, and
effective simulation step. The following domain diagram records these relationships without committing
the implementation to one framework or database library.

6.3.1 High-Level Partitioning

The presentation, application, research, infrastructure, and evidence responsibilities form the principal
partitions. React and FastAPI form the presentation boundary; the orchestrator and traffic-state service
coordinate the application flow; and controllers, perception, routing, and corridor logic contain replace-
able research behavior. The SUMO adapter and repositories isolate external infrastructure, while the
experiment service connects every partition to durable evidence. Figure 6.1 shows their communica-
tion and Table 6.1 states the data each partition may own. Partition boundaries are logical rather than
mandatory network processes. During initial integration, several application modules may run inside
one Python process, provided that they exchange the same validated objects and respect ownership. The
perception worker may be isolated when inference affects timing, and the dashboard remains a separate
client because its refresh rate must not control simulation progress. This partitioning provides a manage-
able deployment for the team while retaining clear seams for profiling, replacement, testing, and later
distribution.

6.3.2 Component Collaboration

Collaboration follows typed requests and events instead of shared mutable objects. At each step the
adapter supplies state, the traffic-state service creates a snapshot, the selected controller proposes an ac-
tion, the safety filter validates it, and the adapter applies the result. Routing publishes immutable route
versions to the corridor coordinator. The experiment service records configuration, actions, mission
CHAPTER 6. HIGH-LEVEL AND LOW-LEVEL DESIGN  74

changes, and metrics. Section 6.6 makes this ordering explicit for normal control, dispatch, and rerout-
ing. Every request carries identifiers that link it to a run, simulation step, controller or mission, and
schema version. The receiving component either produces a validated response or a structured rejection;
it cannot silently repair an incompatible message. Events are delivered to persistence in causal order,
while dashboard streams may omit intermediate views without changing the authoritative record. These
collaboration rules make integration failures observable and allow stubs to replace unfinished modules
during contract testing without bypassing the same validation applied to completed components.

6.3.3 Rationale for Decomposition

The decomposition isolates research algorithms, external tools, and presentation concerns. A controller
or detector can change without receiving direct TraCI authority, while a storage engine or interface li-
brary can change without altering the meaning of a snapshot or applied action. The split also permits
bounded perception execution and deterministic simulation. These benefits justify explicit contracts be-
cause reproducibility and fault diagnosis are central evaluation requirements. A monolithic script could
produce an early visual demonstration, but it would make phase ownership, failure containment, and
comparative evaluation difficult to verify. Conversely, deploying every box as an independent service
would add network failure and configuration overhead before profiling shows a need. The selected mid-
dle position preserves conceptual services behind interfaces while permitting in-process execution. It
supports incremental development: fixed control and simulation can operate before perception or learn-
ing is ready, and later modules can be added without rewriting the control loop or database meaning.

6.3.5 Subsystem Architecture

Each subsystem exposes a narrow testable interface. Controllers return proposed actions, routing returns
versioned paths, the corridor coordinator returns route-bound priority requests, and the traffic-state ser-
vice returns source-specific snapshots. Infrastructure adapters translate these domain objects to TraCI,
HTTP, streams, and persistent records. The domain model in Section 6.5 describes the stable objects
shared across those interfaces. The simulation subsystem owns process launch, stepping, subscriptions,
and applied commands. The experiment subsystem owns configuration validation, lifecycle status, man-
ifests, metrics, and comparison eligibility. The perception subsystem owns jobs, model provenance,
detections, tracks, and derived region observations. The emergency subsystem owns missions, route
versions, priority requests, passage, and recovery. These responsibilities prevent two modules from
writing the same state. Each subsystem can be exercised with fixtures representing adjacent contracts,
allowing tests to distinguish local logic errors from integration or external-tool failures.

6.4 Architectural Strategies

The architectural strategies explain the cross-cutting choices that shape every component: technologies,
reuse, extension points, version control, interface style, storage, and concurrency. Each strategy is stated
together with the reason for it and the cost it introduces. The subsections note where the prototype uses
a simpler form, for example file storage or offline perception.

6.4.1 Choice of Technologies

Python, SUMO, TraCI, FastAPI, React, and structured persistence match the approved proposal and
divide research computation from presentation. Python supports controllers, routing, perception, and
analysis; SUMO supplies reproducible traffic dynamics; FastAPI defines validated contracts; and React
supports independent dashboard views. Versions are written to run manifests. The selected implemen-
tations are Ultralytics YOLO11s with ByteTrack for perception, PyTorch for the Double DQN, and
versioned files instead of a database engine. Selection also reflects team feasibility: these technologies
run locally, expose documented interfaces, and support automated testing without requiring proprietary
traffic infrastructure. SUMO is retained over a throughput-oriented alternative because its network, vehi-
cle, signal, and TraCI tooling align with the approved scope. FastAPI and React add a service boundary
but allow the research core and interface to evolve independently. A technology is not accepted solely
because it is popular; its version, configuration, licence, input assumptions, and effect on timing or
metrics must be recorded for the experiment that uses it.

6.4.2 Reuse of Existing Software Components

Manzil reuses SUMO traffic models, TraCI primitives, OpenStreetMap conversion tools, computer-
vision libraries, and standard graph algorithms. Adapters bound this reuse so an external package cannot
define project semantics implicitly. Imported networks are checked for connectivity and signal legality,
model checkpoints retain provenance, and route costs state their units and observation time. Manzil
contributes experiment, safety, corridor, audit, and comparison logic that combines these components
consistently. Reuse reduces implementation risk but does not transfer responsibility for validation to a
library. The network importer must still confirm turn connections and traffic-light programs; the per-
ception pipeline must still evaluate selected checkpoints and tracking rules on the intended footage; and
the routing service must still build a legal vehicle-movement graph. Third-party defaults are captured in
manifests when they affect results. External components are accessed through project-owned interfaces
so a library upgrade or replacement produces an explicit compatibility change instead of silently altering
stored evidence or control behavior.

6.4.3 Future Extension and Enhancement

Versioned contracts and repository interfaces allow later support for additional corridors, several emer-
gency vehicles, new observation sources, distributed training, or a different simulator. These are ex-
tension points rather than current capabilities. Any extension must preserve single ownership, causal
event ordering, legal phase transitions, and explicit comparison manifests so increased scale does not
weaken the evidence model. Multiple emergency vehicles would require a conflict-resolution policy
rather than simply creating more corridor requests. A live camera source would require privacy review,
calibration, clock synchronization, and monitored failure behavior. Distribution would require authen-
ticated service boundaries and a stronger event-delivery model, while a simulator replacement would
require an adapter capable of reproducing the same snapshot and applied-action semantics. Keeping
these possibilities outside the current claim avoids implying unfinished functionality, yet documenting
their architectural seams prevents short-term choices from closing a reasonable development path.

6.4.4 Version Control

Git maintains source code, schemas, scenarios, and report figures. Each retained experiment records its
commit identifier, dependency lock, model checksum, network and demand versions, controller config-
uration, and metric schema. Demonstration and result releases are tagged. Generated outputs do not re-
place source configuration, and secrets or machine-specific paths are excluded from portable manifests.
Feature work is reviewed through branches or equivalent isolated changes before it is incorporated into
CHAPTER 6. HIGH-LEVEL AND LOW-LEVEL DESIGN  77

an evidence-producing release. Schema and contract changes require coordinated fixtures and migration
notes; a commit that changes the meaning of a metric also increments its definition version. Large model,
video, and run artifacts are referenced by checksums rather than committed indiscriminately. This policy
links every reported result to an inspectable software state while keeping the repository manageable. It
also allows an evaluator to distinguish an exact reproduction from a later rerun made after code, data, or
configuration changed.

6.4.5 User Interface Paradigm

The interface uses task-oriented screens and a unidirectional command-and-view model. Operators con-
figure runs, monitor network and mission state, inspect provenance, and review evidence without directly
manipulating the simulator. Validation errors are tied to fields; colors have textual labels; units and fresh-
ness remain visible; and measured results remain distinct from schematic values. These rules implement
Section 4.8 and permit browser reconnection without transferring control ownership. Screen identifiers
and navigation reflect the user's workflow from configuration through monitoring to comparison, while
specialist details remain available without crowding the overview. Emergency state is displayed with
route version, lifecycle state, and warnings instead of a single ambiguous priority indicator. Analytics
disclose sample count, variability, failed runs, metric definition, and configuration differences near each
comparison. The interface therefore supports operational awareness and academic review, but it never
presents unimplemented fields, schematic charts, or stale streams as measured evidence.

6.4.6 External Database and Data Storage Management

Structured configuration, events, routes, and metrics follow Section 4.9; videos, models, and logs re-
main checksummed external artifacts. A repository interface permits file-backed integration and later
PostgreSQL use without changing domain meaning. FYP-I uses the file-backed form: each run writes
a manifest, metrics, time series, signal events, applied controls, and mission records into its own folder,
and comparisons refuse runs whose network, demand, protocol, or metric versions differ. Immutable
completed-run configuration and versioned metrics protect comparison integrity; schema migrations
and referential constraints are part of the FYP-II database design. Bounded buffering may tolerate a
temporary write failure, but processing stops before evidence loss becomes unbounded. Run manifests
record identifiers and provenance for external artifacts so a run does not depend on an unexplained local
filename. Observation ownership is exclusive, route versions increase monotonically, and priority events
retain the route that justified them. Applied control records are authoritative for evaluation because a
safety intervention may differ from the controller request. Backup and export procedures include mani-
fests and schema versions, while credentials and licensed content remain outside research exports. These
CHAPTER 6. HIGH-LEVEL AND LOW-LEVEL DESIGN                                         78

measures keep storage decisions aligned with auditability rather than treating persistence as a passive
logging concern.

6.4.7 Concurrency and Synchronization

The orchestrator is the only simulation-step owner, and TraCI access is serialized through the adapter.
Controllers receive immutable snapshots and return requests instead of mutating shared state. Perception
uses a bounded queue, dashboard streams may skip views without delaying control, and route publica-
tion is atomic with cancellation of obsolete corridor work. Shutdown rejects new commands, terminates
or detaches SUMO safely, flushes records, and assigns an explicit terminal state. Simulation time, mono-
tonic event sequence, and wall-clock time are stored separately because inference and persistence delays
must not be mistaken for traffic causality. A late observation is marked stale or omitted according to pol-
icy instead of blocking the loop indefinitely. The active route version changes together with invalidation
of its old requests, preventing two paths from owning the same corridor. Database batches may improve
throughput, but applied actions and mission transitions must first enter a durable bounded queue. These
rules define synchronization even when all components run on one machine.

6.7.3 Resource Ownership Tactics

The orchestrator is the only writer to simulation time, and TraCI access is serialized behind the adapter.
Controller computation receives an immutable snapshot and returns a request rather than holding a
reference to mutable global state. Perception uses a bounded work queue; if inference falls behind, the
worker marks observations late or drops work according to a recorded policy instead of blocking control
indefinitely. Dashboard streams are lossy views, so a slow client may skip intermediate snapshots but
cannot delay decisions. Run configuration becomes immutable after start. The current route version is
updated atomically with cancellation of obsolete corridor requests, preventing new and old paths from
owning priority concurrently. Database writes may be batched where safe, but an applied signal event or
mission transition is not acknowledged until it has entered a durable bounded queue. During shutdown,
the API stops accepting new commands, the orchestrator ends or detaches SUMO safely, queued records
are flushed, and the run receives an explicit completed, stopped, failed, or incomplete terminal state.

6.7.5 Implementation Policies

The implementation policies fix the rules that each module family must follow regardless of which
algorithm it contains. They cover controllers, routing, persistence, and the user interface, and they are
the rules that the automated tests check.

6.7.5.1 Controller Policy

All controllers implement a common method that accepts an immutable traffic snapshot, intersection
configuration, and decision context, then returns a request with explanation fields. They cannot write
global state, call TraCI, or suppress the record of a rejected action. The fixed controller, pressure-
inspired controller, and learned policy therefore differ in decision logic while sharing phase identifiers,
decision intervals, safety constraints, and applied-event recording. Deterministic evaluation disables ex-
ploration and seeds every permitted stochastic operation. The safety filter verifies phase membership,
minimum green, required clearance, maximum priority duration, and current ownership before an action
reaches the adapter. If a policy is unavailable, the current legal phase is held and each such decision is
counted; transfer to the configured baseline at a legal boundary is planned for FYP-II. This common in-
terface is central to a fair comparison because it prevents one controller from receiving more permissive
movements or direct simulator privileges. Explanation fields are retained for later error analysis.

6.7.5.2 Routing Policy

The graph builder derives nodes and edges from validated SUMO vehicle movements, including allowed
classes and turn continuity. Cost providers are composable but must state units, observation time, fall-
back behavior, and whether link travel time already includes queue delay. This metadata prevents the
routing service from adding overlapping estimates or comparing seconds with an unnormalized conges-
tion score. A published route plan is immutable, and the mission points to exactly one current version.
Revisions are accepted only through Algorithm 1, which compares paths under one cost snapshot and
applies feasibility, hysteresis, persistence, and cooldown rules. A hard closure overrides ordinary cost
and invalidates an affected remaining path immediately. Before publication, the route is checked from
the ambulance's current edge to the destination and given a revision cause. The routing service never
actuates signals; it supplies versioned plans to the corridor coordinator, which can then cancel or create
priority requests consistently.

6.7.5.3 Persistence Policy

In FYP-I the store writes structured configuration, events, missions, routes, and metrics as versioned
files, and the FYP-II database will add schema migrations and referential constraints, while large videos,
model files, and logs may remain checksummed external artifacts with provenance. Raw high-frequency
state can be downsampled for persistence only when the sampling interval and aggregation rule are
recorded in the metric definition. Completed run configuration is immutable, and derived summaries
retain their source run identifiers and analysis version. Secrets, machine-specific credentials, and un-
portable local paths are excluded from research exports; licensed artifacts are referenced rather than
redistributed when necessary. FYP-I uses a file-backed store behind the repository interface, and Post-
greSQL is planned for structured records in FYP-II. The domain schema and integrity rules remain
independent of that choice so a storage migration cannot change the meaning of an experiment. A
persistence failure follows the bounded behavior in Table 6.4 rather than silently discarding events. Re-
covery records state whether buffered evidence was restored.

6.7.5.4 User-Interface Policy

The user interface is a view and command boundary, not a second control plane. Colors are supple-
mented with text and symbols so congestion, corridor state, or failure is not conveyed by color alone.
Values display their units, source mode, freshness, and invalid state where applicable. Schematic predic-
tions remain visually distinct from measured results, and an uncalibrated video proxy is not labeled as a
physical queue or speed. The interface does not display "time saved" until a valid reference run exists
under the same comparison manifest, and it exposes configuration differences when direct comparison
CHAPTER 6. HIGH-LEVEL AND LOW-LEVEL DESIGN  87

is unsafe. Commands receive validation errors tied to fields, while connection loss leaves the experiment
running and allows a client to reconnect from the current event cursor. These policies implement the
wireframe intentions in Section 4.8 and ensure that a polished display cannot conceal stale data, fallback
intervals, missing runs, or incomplete evidence.

6.7.6 Testing Strategy

Unit tests cover cost functions, route continuity, hysteresis, metric calculations, schema validation, fresh-
ness rules, and corridor transition guards. Property or invariant tests generate action sequences to ensure
incompatible greens are never requested for application, one component owns each intersection, obso-
lete route versions cannot activate priority, and cancellation eventually reaches IDLE through RECOV-
ERY. Integration tests use small SUMO networks to validate single-step ownership, detector-to-state
messages, route application, fallback, and persistence ordering. Scenario tests replay fixed seeds for
normal control, closure rerouting, no-route, invalid actions, and priority timeout; tests for stale data,
controller loss, persistence failure, and dashboard disconnect are planned for FYP-II. Contract fixtures
allow components to be replaced by stubs without weakening field validation. Research verification re-
mains separate from software correctness: passing these tests shows that the implementation follows its
specification, but it does not establish that a policy improves traffic or emergency travel. The matched
experiments in Chapter 5 provide that evidence, while test results explain whether a failed experiment
reflects the policy or a software defect. At the end of FYP-I the automated suite contains 147 tests in
17 files, most of which run real SUMO on small scenarios; they include a random controller over 5,000
steps with zero safety violations, A* against Dijkstra on 200 random cost sets, identical metrics for the
same seed, and a dashboard session from dispatch through closure and rerouting to arrival.

6.7.7 Coding, Build, and Maintainability Policies

Python modules use type hints, Ruff formatting and linting, pinned dependency versions, and docstrings
for public interfaces. React components separate data acquisition from presentation so a visual revision
cannot change experiment ownership. Configuration is stored in validated versioned files rather than
scattered constants, and secrets remain outside exported manifests. The full test suite, including headless
SUMO scenarios, runs before a revision is used for evidence. Experiment releases are tagged and
their commit identifier is written into each run manifest. The repository structure separates application
services, controllers, routing, perception, simulation, dashboard, contracts, scenarios, and experiment
artifacts, as listed in Section 6.7.9. Small interfaces allow a tracker, learned policy, database engine, or
dashboard transport to change without rewriting the central loop, while versioned contracts force such
changes to declare any effect on recorded evidence.

6.7.8 Continuous Integration and Deployment

The proposed continuous-integration pipeline runs formatting, linting, type checks, unit tests, contract
fixtures, schema validation, and a minimal headless SUMO scenario. In FYP-I there is no hosted pipeline
yet: every change is linted and the full test suite, including headless SUMO scenarios, is run before it
is merged into the main branch. A build that changes an interface or metric definition must update its
version and associated fixtures. Deployment for the prototype remains a documented local environment
rather than a claimed production service. A tagged demonstration build includes dependency locks, val-
idated scenarios, required model checksums, and migration state so another team member can reproduce
the same prepared workflow. The headless smoke scenario verifies process launch, one controlled step
sequence, valid signal application, event persistence, and a clean terminal state without requiring the
dashboard. Research experiments are not automatically promoted merely because software tests pass;
the matched evaluation protocol remains a separate activity. Failed checks block an evidence release, and
bypasses must be recorded rather than hidden. If an external model or licensed video cannot be pack-
aged, the build manifest records its checksum and acquisition instructions while keeping the protected
artifact outside the archive.

6.7.9 Source Code Organization

The repository separates API and application services from controllers, routing, perception, simulation
adapters, interface contracts, dashboard code, scenarios, and experiment artifacts. Tests mirror those
boundaries, while generated outputs and large external artifacts remain outside source modules. Con-
figuration is versioned and validated instead of embedded in code. This arrangement keeps research
implementations replaceable, makes ownership visible during review, and avoids circular dependen-
cies between interface, simulation, and persistence concerns. Domain objects and contracts occupy a
low-dependency package that does not import the dashboard or infrastructure adapters. Controller im-
plementations share an interface but do not import each other, allowing fixed, pressure-inspired, and
learned policies to be selected by configuration. Scenario manifests reference networks and demand
files through portable paths and checksums. Analysis scripts read retained records rather than private
controller state. Documentation accompanies public interfaces and configuration schemas. The FYP-I
repository follows this organization. The manzil package contains sim, control, routing, corridor,
experiments, perception, scenarios, and api; dashboard holds the React code, scenarios the
network and signal configuration, kaggle the GPU job definitions, tests the automated tests, and
results the retained summaries and figures. Large datasets and run outputs stay outside version con-
trol and are referenced by checksum.

6.8 Conclusion

The design assigns one clear owner to every mutable resource and makes observation source, simulation
time, units, route version, requested action, and applied action explicit. The high-level architecture keeps
presentation and perception outside the single-writer simulation path, while component responsibilities
and data contracts make integration boundaries testable. The domain model and sequences preserve
causal links from scenario and snapshot through controller request, safety decision, route revision, cor-
ridor transition, and durable event. Guarded recovery and bounded fallbacks ensure that a failure does
not leave an unexplained signal or apparently live dashboard. Common controller interfaces support the
intended progression from fixed and pressure-inspired baselines to a learned policy, and versioned rout-
ing enables a moving corridor without granting the pathfinder direct signal authority. The architecture is
modular enough for team implementation on one machine and leaves distribution as a profiling decision,
not an assumption. It also preserves failed runs and negative research outcomes as evidence instead of
hiding them behind interface behavior.
