Chapter 7 Implementation and Test Cases

This chapter describes how the design of Chapter 6 was implemented during FYP-I and how the im-
plementation was tested. The first part explains each module in the order in which data flows through
the system: the road network and demand, the simulation adapter and safety filter, the three signal
controllers, ambulance routing, the green corridor, the perception pipeline, the dashboard, and the ex-
periment runner. The second part presents the test-case design, a set of representative test cases, and the
test metrics, including a traceability matrix that links every functional requirement to its implementation
status and its tests. All code is in the project repository, and every number quoted here comes from a
recorded run or test.

7.1 Implementation

Manzil is implemented as one Python package, manzil, together with a React dashboard and a set of
Kaggle job definitions. All simulation, control, routing, and experiment code runs in a single Python
process on the team laptop or a cloud Linux machine, while detector training and video tracking run as
GPU jobs on Kaggle. Table 7.1 links each component of the architecture in Figure 6.1 to the module that
implements it. The logical boundaries of the design are kept as module boundaries: only the simulation
adapter imports TraCI or libsumo, and every controller and the corridor coordinator reach SUMO only

7.1.1 Development Environment

The software versions are pinned in the project configuration file so that the laptop and the cloud ma-
chines install identical packages. SUMO 1.28.0 is installed from the Python package index together with
libsumo, TraCI, and sumolib, which removes the need for a separate system installation. Python 3.10
runs on the laptop and Python 3.13 in the cloud sessions, PyTorch 2.9.1 (CPU build) trains the DQN,
and Ultralytics 8.4.210 provides YOLO11s and ByteTrack on Kaggle. Kaggle jobs are pushed and their
small outputs, such as metrics, plots, and model weights, are pulled back with the Kaggle command-line
tool, so the 9.9 GB UA-DETRAC dataset never leaves Kaggle. Code style is checked with Ruff and the
tests run with pytest before every change is merged into the main branch.

7.1.2 Synthetic Network and Demand Generation

The test network is generated by manzil/scenarios/grid.py, which calls SUMO's netgenerate.
It produces a 3×3 grid with 200 m blocks, two lanes per direction, a 50 km/h speed limit, nine four-
arm signalized junctions labelled A0 to C2, and twelve dead-end fringe roads through which traffic
enters and leaves. A record file stores the generation command, the SUMO version, and a checksum
of the network content, so a rebuild can be checked against the committed file. The network reader
in manzil/sim/network.py extracts, from the network file alone, every controlled signal link, its
approach and exit lanes, the legal green phases, and SUMO's conflict matrices. The reader is network-

independent: a test runs it on a 4×4 grid as well.

Demand is generated by manzil/scenarios/demand.py. Each entry road receives vehicles from a
seeded Poisson process, destinations are drawn uniformly among the exit roads without U-turns, and
SUMO's duarouter computes the routes. Table 7.2 lists the four profiles. The rates were chosen with
a sweep under SUMO's default signals so that every profile runs without gridlock: at 750 vehicles per
hour per entry road the network already jammed. On five seeds with default signals, all 20 check runs
finished with no teleports and no collisions.

7.1.3 Simulation Adapter and Safety Filter

The simulation adapter in manzil/sim/adapter.py is the only module that starts SUMO, steps it,
reads its state, and writes signal states. It offers two interchangeable back ends with one interface:
libsumo, which runs SUMO inside the Python process and is used for experiments, and TraCI, which
runs SUMO as a separate process and is used for the dashboard and the graphical viewer. At each step
the adapter reads lane subscriptions and returns a typed snapshot with, for every approach, the vehicle
count, halting vehicles, waiting time, mean speed, and occupancy. A missing speed on an empty lane is
reported as missing rather than zero. One step of the grid with medium demand takes about 1 ms.

The safety filter in manzil/control/safety.py implements the safe-transition rules of Section 6.7.1.
Controllers only submit a request for a green phase; the filter decides when it is applied. It holds a change
until the current green has lasted the minimum of 10 s, inserts 3 s of yellow and 2 s of all-red, and then
shows the new green. Requests during a transition and unknown phases are refused. A maximum-red
guard forces service of any phase that has been red for 85 s, so that with clearance no phase waits longer
than 90 s. Every switch or intervention is stored as an applied-control record with the requested and
applied phase, the intervention type, the simulation step, and the reason. An independent safety monitor
checks every signal state actually shown in SUMO against the conflict matrix, the declared phases, the
yellow duration, and the minimum green, and the number of violations is a metric of every run.

7.1.4 Signal Controllers

All controllers implement the same interface in manzil/control/base.py: they receive the traffic
snapshot and return phase requests. The fixed-time controller requests the phase whose window contains
the current time within the cycle. Its plans were tuned for each demand profile on development seeds
100 and 101 only. The resulting north­south and east­west greens are 20/20 s for light, 25/25 s for
medium, 45/45 s for heavy, and 45/25 s for uneven demand. A second fixed-time arm uses one 35/35 s
plan for every profile.

The adaptive controller implements Equation 5.2. For each phase it adds the queues of the incoming
lanes it serves, subtracts  times the queues of the lanes it feeds, and adds  times the longest waiting
time among its approaches. Each incoming lane is counted once per phase even when it feeds two
movements. The controller keeps the current phase until a minimum hold has passed, switches only
when another phase scores higher by a margin, and forces a switch at maximum green. One parameter
set was selected from 60 settings on the development seeds and is used for every profile:  = 0.5,
 = 0.02, maximum green 40 s, maximum red 90 s, switching margin 3, and minimum hold 15 s. Every
request carries its scores, so each switch can be explained afterwards.

The learned controller is a parameter-sharing Double DQN [3]. It is implemented in PyTorch [26], with

the agent in manzil/control/dqn.py and the environment in manzil/control/rl_env.py. One

network serves all nine junctions. Each junction builds a 26-value observation: for up to four approaches

in compass order the halting vehicles, vehicles, waiting time, and whether the approach has green; for

each phase a current-phase flag and its pressure; and the elapsed green time and a transition flag. Actions

are masked so that the agent can only keep the phase before the minimum green and cannot interrupt a

transition. The reward is

7.1.5 Ambulance Routing and Rerouting
The routing graph in manzil/routing/graph.py uses SUMO edges as nodes. An arc joins two edges

only when SUMO has a lane connection between them that an emergency vehicle may use, so every
route can be driven and contains no U-turns. The edge cost follows Equation 5.4: the free-flow running
time at the currently reported speed limit, plus 2 s per halting vehicle divided by the number of lanes,
plus a declared 10 s signal delay on signalized edges, and an infinite cost for a closed edge. Snapshots
older than five steps or with negative costs are rejected. Dijkstra is the reference search. A* uses the
straight-line distance divided by the maximum speed, scaled by 0.896, the smallest ratio of edge length
CHAPTER 7. IMPLEMENTATION AND TEST CASES  95

to node distance on the grid. The scaling is needed because SUMO edge lengths exclude the junction
interiors, and it keeps the heuristic admissible.

The mission logic in manzil/routing/mission.py implements Algorithm 1. The route is refreshed
every 5 s from the ambulance's current edge. A closure on the remaining route is accepted at once.
Otherwise a cheaper route is adopted only if it saves more than  = 10 s for at least  = 10 s, with a 30
s cooldown after each revision. Each accepted route becomes a new numbered version with its trigger,
and rejected candidates are logged. Static routing, used as the comparison arm, plans once on free-flow
costs at dispatch.

7.1.6 Green Corridor

The corridor coordinator in manzil/corridor/coordinator.py implements Algorithm 2 with a look-
ahead of the next two signalized junctions on the ambulance's remaining route. A junction is requested
when it enters the look-ahead and activated when the ambulance's free-flow arrival time is within 15
s plus the time needed to clear the queue on its approach. Activation gives the corridor ownership of
that junction in the safety filter, so normal requests are held, and the corridor requests the phase that
serves the ambulance's movement. Priority lasts at most 60 s. Passage is detected when the ambulance
leaves the approach edge, after which ownership returns to normal control through the safety filter, and
recovery lasts until the junction's queue is back to its mean of the 120 s before activation. A route
revision cancels requests at junctions that are no longer on the route.

A live dashboard run showed the ambulance stopping at red lights on its route, so the team added a per-
second record of why the ambulance stood still and measured it in 20 runs per background controller.
The main cause was a defect. After a route revision, SUMO keeps the edges already driven in the
vehicle's route, so SUMO's route index was ahead of Manzil's route plan, and the corridor skipped the
junction directly ahead of the ambulance. The coordinator now finds the ambulance's position by edge.
With this fix the ambulance was never first in line at a red light at a corridor junction. Its remaining stops
were vehicles queued in front of it and a permissive left turn at the final junction.

Four further changes were then tested on medium and heavy demand with five seeds and both fixed-time
and DQN background control: earlier activation with a look-ahead of three junctions, shortening the
current green for a corridor request, making ordinary vehicles give way with SUMO's blue-light device,
and all three together. Only the shortened green was kept. In the resulting version of the corridor, a
corridor request may end the current green after 5 s instead of the normal 10 s. Yellow and all-red are
never shortened, normal control always keeps the full 10 s, and the safety monitor treats a green shorter
than 10 s as a violation unless the corridor owns the junction, and a green shorter than 5 s as a violation in
CHAPTER 7. IMPLEMENTATION AND TEST CASES                                                96

every case. Earlier activation gave small and inconsistent gains while increasing cross-street queueing
by 4 to 14 percent. The blue-light device made the ambulance cross red lights; once red lights were
enforced again, it caused gridlocks, because it needs SUMO's sublane model. It remains an option that
is off by default. The measured effects are reported in Chapter 9.

7.1.7 Vehicle Detection, Tracking, and Counting

Perception runs as three Kaggle jobs on two Tesla T4 GPUs. The first job, kaggle/yolo_data, builds
the training data. UA-DETRAC labels four vehicle types, which are mapped to the project classes: car
and van to car, bus to bus, and others to truck. Every tenth frame is used to avoid near-duplicates, regions
that UA-DETRAC marks as ignored are filled grey, and the validation set consists of six whole training
sequences, so frames of one sequence never appear in two splits. UA-DETRAC has no motorcycle
labels, so COCO 2017 [27] images that contain a motorcycle are added, with all four classes labelled, to
stop the detector from forgetting that class. Table 7.4 gives the resulting splits.

The second job, kaggle/yolo_train, fine-tunes the COCO-pretrained YOLO11s [5] for 50 epochs at

The counting logic in manzil/perception/counting.py is shared between the Kaggle job and the
local tests. A full-width line is placed at 60 percent of the image height, and a track is counted once,
when its box centre crosses the line, with its class taken as the majority over the track. Crossings inside
ignored regions are dropped. Because UA-DETRAC gives true track identities, true counts are produced
by passing the annotated boxes through the same counter, so the count error measures detection and
tracking only. UA-DETRAC has no stop lines, so the queue indicator is a proxy: the number of tracked
vehicles that moved less than a quarter of their box height in one second. A Kaggle script job must be a
single file, so a build script copies the counting module into the job, and a test fails if that copy is out of
date.

7.1.8 Dashboard and API

The FastAPI service in manzil/api/ serves the built dashboard and the API on port 8000. One live run
executes in a worker thread with the same step order as the batch runner: snapshot, routing, corridor,
controller, safety filter, and adapter. Dashboard commands such as dispatching an ambulance or closing a
road are queued and executed between two simulation steps, so only the worker thread touches SUMO.
The live run uses the TraCI back end, so a SUMO failure cannot stop the API. The API offers run
start, stop, and speed, network geometry, current state, ambulance dispatch, and road closure, and a
WebSocket stream sends the state about ten times per second.

The dashboard in dashboard/ is written in React 19 and TypeScript and built with Vite. It draws the
network as plain SVG from the geometry in the SUMO network file. It shows the signal colour of
every link at its stop line, the vehicles, queue shading on each road, closed roads, the ambulance with its
current route version, and the corridor state of each junction. Chapter 8 explains how to use it.

7.1.9 Experiment Runner and Reproducibility

The runner in manzil/experiments/runner.py validates a run configuration before starting SUMO
and then executes Algorithm 3. Each run writes a folder with a manifest holding the configuration and
its digest, the seed, the Manzil, SUMO, and Python versions, the Git commit, the network checksum, the
demand record, the signal plan, the safety timing, and the termination reason. Next to the manifest are the
metrics, a 60 s time series, the signal events, the applied controls, and, for emergency runs, the mission
record with route versions, corridor events, and stop reasons. The batch tool runs controller arms,
demand profiles, and seeds in parallel processes, and the comparison tool computes means, standard
deviations, paired differences with 95 percent confidence intervals, and the number of seeds on which
an arm was better. The comparison tool refuses to compare runs whose network, demand generator,
protocol, or metric versions differ.

7.4 Conclusion

The FYP-I implementation turns the design of Chapter 6 into a working prototype: a reproducible
SUMO grid with seeded demand, a single simulation adapter, a safety filter that every controller must
pass through, three signal controllers including a trained DQN, time-based routing with closure-triggered
rerouting, a moving green corridor, a fine-tuned detection, tracking, and counting pipeline, and a live
dashboard. The implementation also uncovered problems that a demonstration alone would have hidden,
namely a misleading travel-time metric, a starvation case that led to the maximum-red guard, and the
corridor's route-index defect, and each was fixed and covered by a test. All 147 automated tests pass.
Chapter 8 explains how to operate the prototype, and Chapter 9 reports the experiments run with it.
