Chapter 7 Implementation and Test Cases

This chapter describes how the design of Chapter 6 was implemented during FYP-I and how the im-
plementation was tested. The first part explains each module in the order in which data flows through
the system: the road network and demand, the simulation adapter and safety filter, the three signal
controllers, ambulance routing, the green corridor, the perception pipeline, the dashboard, and the ex-
periment runner. The second part presents the test-case design, a set of representative test cases, and the
test metrics, including a traceability matrix that links every functional requirement to its implementation
status and its tests. All code is in the project repository, and every number quoted here comes from a
recorded run or test.

7.1 Implementation

Manzil is implemented as one Python package, manzil, together with a React dashboard and a set of
Kaggle job definitions. All simulation, control, routing, and experiment code runs in a single Python
process on the team laptop or a cloud Linux machine, while detector training and video tracking run as
GPU jobs on Kaggle. Table 7.1 links each component of the architecture in Figure 6.1 to the module that
implements it. The logical boundaries of the design are kept as module boundaries: only the simulation
adapter imports TraCI or libsumo, and every controller and the corridor coordinator reach SUMO only
through the safety filter.

7.1.1 Development Environment

The software versions are pinned in the project configuration file so that the laptop and the cloud ma-
chines install identical packages. SUMO 1.28.0 is installed from the Python package index together with
libsumo, TraCI, and sumolib, which removes the need for a separate system installation. Python 3.10
runs on the laptop and Python 3.13 in the cloud sessions, PyTorch 2.9.1 (CPU build) trains the DQN,
and Ultralytics 8.4.210 provides YOLO11s and ByteTrack on Kaggle. Kaggle jobs are pushed and their
small outputs, such as metrics, plots, and model weights, are pulled back with the Kaggle command-line
tool, so the 9.9 GB UA-DETRAC dataset never leaves Kaggle. Code style is checked with Ruff and the
tests run with pytest before every change is merged into the main branch.

7.1.2 Synthetic Network and Demand Generation

The test network is generated by manzil/scenarios/grid.py, which calls SUMO’s netgenerate.
It produces a 3×3 grid with 200 m blocks, two lanes per direction, a 50 km/h speed limit, nine four-
arm signalized junctions labelled A0 to C2, and twelve dead-end fringe roads through which traffic
enters and leaves. A record file stores the generation command, the SUMO version, and a checksum
of the network content, so a rebuild can be checked against the committed file. The network reader
in manzil/sim/network.py extracts, from the network file alone, every controlled signal link, its
approach and exit lanes, the legal green phases, and SUMO’s conflict matrices. The reader is network-

Demand is generated by manzil/scenarios/demand.py. Each entry road receives vehicles from a
seeded Poisson process, destinations are drawn uniformly among the exit roads without U-turns, and
SUMO’s duarouter computes the routes. Table 7.2 lists the four profiles. The rates were chosen with

hour per entry road the network already jammed. On five seeds with default signals, all 20 check runs
finished with no teleports and no collisions.

7.1.3 Simulation Adapter and Safety Filter

The simulation adapter in manzil/sim/adapter.py is the only module that starts SUMO, steps it,
reads its state, and writes signal states. It offers two interchangeable back ends with one interface:
libsumo, which runs SUMO inside the Python process and is used for experiments, and TraCI, which
runs SUMO as a separate process and is used for the dashboard and the graphical viewer. At each step
the adapter reads lane subscriptions and returns a typed snapshot with, for every approach, the vehicle
count, halting vehicles, waiting time, mean speed, and occupancy. A missing speed on an empty lane is
reported as missing rather than zero. One step of the grid with medium demand takes about 1 ms.

The safety filter in manzil/control/safety.py implements the safe-transition rules of Section 6.7.1.
Controllers only submit a request for a green phase; the filter decides when it is applied. It holds a change
until the current green has lasted the minimum of 10 s, inserts 3 s of yellow and 2 s of all-red, and then
shows the new green. Requests during a transition and unknown phases are refused. A maximum-red
guard forces service of any phase that has been red for 85 s, so that with clearance no phase waits longer
than 90 s. Every switch or intervention is stored as an applied-control record with the requested and
applied phase, the intervention type, the simulation step, and the reason. An independent safety monitor
checks every signal state actually shown in SUMO against the conflict matrix, the declared phases, the
yellow duration, and the minimum green, and the number of violations is a metric of every run.

7.1.4 Signal Controllers

All controllers implement the same interface in manzil/control/base.py: they receive the traffic
snapshot and return phase requests. The fixed-time controller requests the phase whose window contains
the current time within the cycle. Its plans were tuned for each demand profile on development seeds
100 and 101 only. The resulting north–south and east–west greens are 20/20 s for light, 25/25 s for
medium, 45/45 s for heavy, and 45/25 s for uneven demand. A second fixed-time arm uses one 35/35 s
plan for every profile.

The adaptive controller implements Equation 5.2. For each phase it adds the queues of the incoming
lanes it serves, subtracts α times the queues of the lanes it feeds, and adds β times the longest waiting
time among its approaches. Each incoming lane is counted once per phase even when it feeds two
movements. The controller keeps the current phase until a minimum hold has passed, switches only
when another phase scores higher by a margin, and forces a switch at maximum green. One parameter
set was selected from 60 settings on the development seeds and is used for every profile: α = 0.5,
β = 0.02, maximum green 40 s, maximum red 90 s, switching margin 3, and minimum hold 15 s. Every
request carries its scores, so each switch can be explained afterwards.

The learned controller is a parameter-sharing Double DQN [3]. It is implemented in PyTorch [26], with

the agent in manzil/control/dqn.py and the environment in manzil/control/rl_env.py. One

network serves all nine junctions. Each junction builds a 26-value observation: for up to four approaches

in compass order the halting vehicles, vehicles, waiting time, and whether the approach has green; for

each phase a current-phase flag and its pressure; and the elapsed green time and a transition flag. Actions

are masked so that the agent can only keep the phase before the minimum green and cannot interrupt a

transition. The reward is
